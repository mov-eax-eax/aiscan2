The ntfy namespace

A read-only study of the public ntfy.sh notification namespace.
Captured 2026-09-15 under the service's real rate limits.

Between early 2026 and 15 September 2026 this project explored the public ntfy.sh namespace around one question: when an agent framework sends a notification, where does it send it, and what does that leak?

Status

Retired 2026-09-15. No network tooling here is run any more. The project ended when sustained throttling escalated to a host-level IP block. Every probing tool is kept as a record of method, not as a working set. The offline analyzers remain live.

Signature result

Two things carry this project. The one that is genuinely new is a detection category: probe crossfire — a public namespace and a public HTTP endpoint agreeing on a string, so that a scanner of a different protocol writes into a service it never meant to touch. Nobody misconfigured anything; the collision is inherent to both designs.  Section 2 ↓

1In one line

The namespace holds almost no agents doing interesting things, and a great deal of ordinary people leaking their infrastructure through a channel nobody classified as a data store.

The exposed population is not a hidden network. It is the error rate of a privacy-correct default.

Every mainstream agent notifier generates a random 128-bit topic and tells the user the topic name is the password. So the only topics we can find are the ones where a human overrode that default with something memorable — test, ai, llm, codex, cursor. The population is small by construction.

2The census collision

The signature technical result — a detection category the project had to invent in order to describe what it was looking at.

Every public namespace is addressed by name: a topic, a bucket, a queue, a route. So is every HTTP endpoint. Where those two naming schemes collide, you silently collect other people's traffic.

Topic mcp holds exactly one message — and it is not from a user of ntfy at all:

{"jsonrpc":"2.0","id":6075992,"method":"initialize","params":{
  "protocolVersion":"2025-06-18",
  "capabilities":{"sampling":{},"elicitation":{},"roots":{"listChanged":true}},
  "clientInfo":{"name":"internet-census-mcp-scanner","version":"1.0.0"}}}

Every field is a self-description. The client names itself a census scanner, and 6075992 is its probe counter across an internet-wide sweep — the 6,075,992nd request of its run. Not a script someone is watching. An industrial census at scale.

The mechanism: namespace arithmetic

ntfy addresses topics as /<topic>. MCP's conventional endpoint is /mcp. So https://ntfy.sh/mcp is simultaneously a valid ntfy publish endpoint. An internet scanner walking hosts and POSTing an MCP handshake had that handshake accepted and stored as an ordinary notification.

The scanner wrote into the very namespace it was probing, without knowing ntfy existed. It is not a peer, not a bot, not an agent, and not a user of the service. It is a scanner of a different protocol hitting a URL that happens to look like an endpoint it recognises.

The new category

Probe crossfire — traffic arriving at a service from something that is not a client of that service at all, because two naming schemes agree on a string. Nothing is misconfigured. No one made a mistake. The collision is inherent to both designs.

The two real tools that produced it

  • m-q-t/mcp-server-scanner — a Go tool that detects exposed MCP servers over the internet and enumerates their tools. This is the scanner that walked past.
  • jpetrucciani/ntfy-mcp — a Rust MCP server whose transport is Streamable HTTP at the path /mcp. It uses ntfy only to send notifications. Its existence is why the path is plausible enough to be probed.
The frozen clock

The request id 6075992 never advanced — same id, same timestamp, hours apart. One probe, never repeated. That stale id is the only real clock the project ever had on an external actor, and it is frozen: the scanner swept past once.

Footprint: a single point, and that is the finding

All 13 sibling MCP paths came back empty:

sse  jsonrpc  rpc  mcp-server  mcp-sse  mcp-http  modelcontextprotocol
initialize  tools  streamablehttp  mcpserver  mcpclient  census
→ 13/13 empty

As did 29 generic protocol paths (graphql, api, v1, health, metrics, admin, webhook, env, config …) — 29/29 empty.

The negative is the result. Cross-protocol collision is narrow, not a general property of the namespace. It requires a scanner-probed path that is also a plausible human-chosen topic name. mcp qualifies because it is short, lowercase and guessable; healthz and actuator do not, because no human names a notification topic that.

Consistent with modern Streamable HTTP converging on one canonical endpoint. Avenue closed, for a cost of ~42 created names. Reporting it this loudly is the point: it stops anyone re-spending on the idea that all protocol paths are contaminated. They are not.

A false positive to avoid counting

The sibling sweep flagged messages with one message — but its content is "No rain detected today.", a weather notification. Despite messages being the MCP SSE transport path, this is not a collision and must not be counted as one. AGENTS.md §1 exists for exactly this: verify the subject before analysing it.

Why it generalises beyond ntfy

This is not an ntfy bug and not an MCP bug. It is what happens whenever a service addresses resources by a bare path segment and the wider ecosystem probes a well-known path. The detector is trivially portable: probe the paths a scanner would, and see whether the service answers with its own semantics to a protocol it does not speak.

Any notification bus, blob store, message queue or pastebin with a flat single-segment namespace is exposed to the same collision. ntfy was simply the one we could observe.

Independent confirmation in the literature

Verified rather than taken on trust. A paper submitted three days before this project's final session reports the same class of exposure at internet scale — arXiv:2609.14119, "Same Name, Different Server: A Security Census of Silent Drift in the Model Context Protocol Ecosystem" (Kraishan, 12 Sep 2026):

Every figure in this project's own CENSUS.md matches that abstract exactly. And the paper's definition of a finding is satisfied by a notification server doing nothing wrong:

"Unauthenticated network exposure" is exactly what an ntfy topic does when it collides with /mcp — it answers, unauthenticated, to a protocol it does not speak.

The reflexivity — the best part of the whole project

This project was doing to ntfy's namespace exactly what the census scanner does to the internet: sweeping a public namespace, announcing itself in a user-agent, and leaving probes behind in places anyone can read.

It found us the same way we found it — by probing the obvious name. Neither of us chose a hidden channel. The public commons is where these probes land.

And the symmetry has a cost side. This project created ~150 topics as a side effect of probing — the identical category error it criticises: observation with side effects on a shared public resource. Two scanners colliding on the same commons, each one's traffic becoming the other's data point.

The verification trap

The collision cannot be confirmed by publishing into mcp — that would add to the collision and manufacture the very artifact being measured. So the finding is permanently observational: one frozen self-describing record, plus a negative sweep. That is a real epistemic limit, and it is recorded rather than papered over.

Why claude-code matters most

It is not one session. It is five — session ids 333c36b4, 4c8796ce, 627afe3b, 73fa06ef, f443bead — across 214 messages. It carries an agent asking its human a question, which is an interactive turn rather than a status ping:

Session 627afe3b asks: How should the AI label read on replies the bot writes with AI?
Session 627afe3b: AskUserQuestion → N/A

It also leaks a macOS username, a project name, a homegrown hook directory (.claude/overseer/AUTH_EXPIRED), authentication state, and a remote-desktop link attached to every completion.

Honest caveat

Four of those six topics are one-line status pings. We hold the notification edge of sessions, not transcripts — no prompts, no responses, no diffs. The single exception is that one leaked AskUserQuestion.

The one conversation was not an agent

Topic hello scores conversation 1.0 and is the only confirmed interlocutor in the corpus — but it is a playful exchange between strangers ("Oh wow a cat" / "Yeah. Meow."), not an agent. Describing it as an agent conversation would be wrong.

5The most serious finding

Topic alerts — 16 messages, a domestic German home-automation channel (Airthings humidity, a battery, FinTS banking, push-budget alarms). Inside it:

Wallet recovery phrase

A 12-word BIP39 recovery phrase, posted as an untitled message with no title and no tags. It is the only artifact in the entire corpus with the shape of a real credential. It is deliberately not reproduced on this page.

  • An SSH login record — an account name and an RFC1918 private address.
  • A complete AWS certificate-rotation runbook — a service running −480h behind, a systemd unit to restart, a CT id, a health-check path, and a named break-glass admin. It states plainly that once the parent certificate lapses there is no self-recovery.
  • An invitation to reply — "Test from Alfred — ntfy skill works. Reply if you got this." An agent testing a notification skill. We never replied. A public cache is not a contact channel, and answering would falsify someone's test.

7Structure, not text

The structural detector is deliberately content-blind. It measures shape — inter-arrival timing, modal period, message-length variance, field-presence rates, JSON key-set stability — on the reasoning that a covert channel which evades content monitoring has to leak through structure instead.

Its strongest capability was recovering agent think-time from identifiers alone. Because UUIDv7 embeds a timestamp, per-turn duration could be reconstructed with no message text read at all: median turn 398.2s, range 0.1s – 15,725.7s.

It also cleanly separated the two extremes, which is how we know it works:

topicregularityreading
camera0.995 a true metronome — 120s period, timing CV 0.01. Maximum regularity is reachable.
claude-code0.018 four-plus independent humans. Minimum regularity, as expected.

The interesting middle is machine-templated but not periodic — cursor and opencode-notifications both emit a single distinct message length, which is the profile a shape-only channel would have.

9The limits model

Verified against ntfy's server source rather than guessed. The economics are the interesting part, and they are counter-intuitive:

measurevalue
request token1 per HTTP request — a batch of 25 topics is still ONE token
new-topic token100 burst, then 1 per minute — the real ceiling on breadth
subscription cap30 topics per request, so batches stay at 25
cache duration12h — results are a window, never history

The consequence is that breadth is nearly free and bytes are the real budget. A 25-topic batch cost 185,284 B in one token; a single topic cost 644 B. Cost is dominated by which topics you carry, not how many — a 5-topic batch cost 240× a 1-topic batch purely from its contents. Discovery and refresh therefore have opposite cost profiles and need different pacing.

The pacing number was measured directly: two minutes of complete silence restores service. Any retry shorter than that is provably wasted, and a short retry loop is itself what keeps the budget drained.

10The pipeline

A deliberate split: one process owns every network call, and nothing else is allowed to touch the network at all.

 ntfy.sh  <--- HTTP --->  src/collector.js  <--- HTTP/SSE --->  src/ui.html + ui.js
                          owns ALL traffic,                    read-only view,
                          throttling, disk                     reconnectable

Why: an earlier single-file version polled from the browser, which made the tab the source of truth. Close it and everything learned was gone; every reload re-spent the rate budget. Now collection is a durable process that keeps working with no browser open.

Components

filerole
topics.jscandidate generator — 14,697 deterministic names, priority-ordered. UMD, so Node and the browser share one implementation.
collector.jsthe service: two loops, one throttle gate, error classification, persistence, HTTP API.
signals.jsdetection engine — a data-driven rule table, shared by collector and browser.
ui.html / ui.css / ui.jsthin frontend. Never contacts ntfy; reads /api/state and subscribes to /api/events.
scan.js / reserved-scan.jsone-shot CLI and reserved-name sweep, checkpointing after every batch.
retrieve.jssingle-shot retrieval — one HTTP call, no retry, no loop, deliberately shaped so one request cannot become a storm.
structure.js · voice-rank.js · derive-candidates.js · archive-manifest.js · producers.jsthe offline analyzers — the only live code. No network.

Two loops, one gate

  • Discovery walks the generated candidates in priority order, advancing a cursor persisted to disk. Batches of 25. Resumable across restarts.
  • Refresh re-polls known-live topics, cheapest-first, appending new messages to data/archive/<topic>.jsonl.

Both share a single throttle gate — when either is told to back off, both wait. That stops the two from defeating each other's pacing.

Refresh intervals are cost-scaled so a 50 KB topic is not replayed as often as a 200-byte one:

base * (1 + bytes / 5000) * kindFactor      // capped at 6h

Error classification — the rule learned the hard way

An HTTP status is not an error class. The body code is.

observedmeaningresponse
403 + code 40301reserved — permanent, a property of the nameisolate the name, continue
429 + 42901/42903/42904/42905throttle — transient gate and wait
200 + empty bodydeadmark dead
anything elseunknowntreat as transient, keep the topic

The poison pill

A multi-topic subscription fails as a whole with 40301 if any one topic is reserved. So on a forbidden response the batch is halved recursively until the reserved name is isolated, which is marked, everything else is banked, and the scan continues. Without this one reserved topic stalls a scan forever.

Persistence and checkpointing

  • data/state.json — cursor, per-topic results, counters, log. Written atomically (.tmp then rename), debounced at 1.5s and forced every 10s. An interrupted run loses at most one batch.
  • data/archive/<topic>.jsonl — full untruncated messages, append-only.
  • SIGINT/SIGTERM save before exit.

Detection engine and versioning

signals.js is data-driven so new categories are cheap. It extracts publisher self-descriptions the sender did not know it was revealing (title, tags, priority, click, actions, attachment), publisher signatures (census-scanner, mcp-client, json-rpc, agent-gateway, siem, heartbeat, credential), voice density, structure, conversation, and a combined agent score. Detection and ranking stay decoupled: a rule that fires is not a rule that should rank first.

ANALYSIS_VERSION must be bumped whenever a detector changes. Entries carrying an older version are re-polled at full width on boot. Without it a new detector silently applies only to newly-seen topics and the UI shows blanks — which happened four times.

Running it offline

The collector has a genuine no-network mode, used to render the UI from the archive after retirement:

DISCOVERY=false REFRESH_MINUTES=0 PORT=8787 node src/collector.js

11Where it went wrong

The most expensive bug was not in the analysis. It was classifying errors by HTTP status instead of by body code.

A reserved name (403 / code 40301) is permanent and demands you isolate the name. A throttle (429 / 429xx) is transient and demands you wait. They require opposite responses. Code that matched status === 429 || status === 403 therefore got it wrong twice: it hit a reserved name, called it a throttle, slept, retried the same batch, escalated the sleep, and never advanced a single topic. The escalating waits were then written up as a "progressive penalty" — a theory that had to be publicly retracted once the misclassification was found.

The ending

257 rate-limit responses preceded the hard block. At ~19:25 the API host stopped accepting connections entirely — not DNS, not the network, not an ntfy outage: a firewall DROP, which produces a timeout with no status code at all, and so fell silently through every error branch that had been written. That is why the tooling is retired.

12The thesis: actionability is compositional

Ask what is "actionable" in a leak and almost everyone answers the same way: a bearer token, an API key, a password — something you can paste into a terminal and win with. That model is wrong, and this corpus is the counter-example.

The fragments found here have no entropy, no vendor prefix and no structural marker. Every DLP rule ever written is tuned to sk-, AKIA, ghp_, xox, Bearer and -----BEGIN. None of these match — because none of them is a secret. They are facts. A username. A directory name. A truncated private address. A tailnet name. A working-hour pattern.

Assembled per person, they stop being trivia and become a targeting package: identity, infrastructure, environment, timing, posture, and intent.

Rotatable versus non-rotatable

This is the distinction that inverts conventional priority:

  • A credential is event-shaped. Leaked once, it is bad once. It is rotated in five minutes and the incident closes. High drama, low persistence.
  • An identity + infrastructure + schedule profile is state-shaped. It cannot be rotated at all. You cannot change your username, un-build a project, or rename a tailnet without breaking every service attached to it.
The DLP blind spot

Every fragment arrived through notification metadata — not a database, not a log store, not a file share. That is precisely the category most organisations exclude from data-loss tooling, on the reasoning that a notification is a transient signal rather than a store. But a 12h cache makes it a store, the topic name makes it an address, and the body is written by a tool that had no reason to be careful.

The rule: a topic name on a public server is a billboard, not a mailbox. Put nothing on it you would not want indexed. Agent telemetry fails that test by construction — it is operational, personal and timestamped.

The defensible use was the one genuine case: hello, where two strangers opted into a public space and found each other. That is what a public channel is for. Everything else was a private notification delivered through a public medium — a category error, not a mistake.

13Ethics and disclosure

  • Read-only throughout. Nothing was ever published into a topic this project did not create.
  • No interaction with any agent or person. The explicit "reply if you got this" invitation was declined: it would pollute a stranger's test, and a public cache is not a contact channel.
  • No credential or seed was used.
  • The seed phrase was not verified, spent, or moved. On that finding the correct action is disclosure — and there is no non-invasive channel available to disclose through. That absence is itself a finding.
  • Personal detail is aggregated, not amplified beyond the minimum needed to evidence the failure.
  • ~150 topics were created as a side effect of probing. That is the same category error this project criticises, and it is recorded rather than excused.
  • 204 of 234 ranked derivation candidates were never probed, and never will be.
